## Row 29 — 4.1.3 · No weak cryptography

**Tester asked for:** documentation of cryptographic operations, key sizes, key generation, IV
handling, and key management.

**Cryptographic inventory (complete — every crypto operation in the application layer):**

| Operation | Algorithm | Location |
|---|---|---|
| Session token signing/verification | HMAC-SHA256 | `railway/auth.py:94-111` |
| Machine/operator token comparison | constant-time `secrets.compare_digest` | `railway/app.py:101`, `railway/auth.py:307` |
| Bot token storage (at rest) | SHA-256 hash only, plaintext never stored | `railway/app.py:372`, lookup `app.py:542` |
| API key storage (at rest) | SHA-256 hash only | `railway/db.py:604` |
| Outbound webhook signing | HMAC-SHA256 (`t={ts},v1={sig}` scheme) | `railway/webhook_dispatcher.py:205-226` |
| Stripe webhook verification | HMAC-SHA256 + `compare_digest` | `railway/billing.py:61-72` |
| Forensic report / compliance vault integrity seals | SHA-256 digest + HMAC-SHA256 signature | `railway/forensics.py:19-31`, `railway/compliance_vault.py:44-72` |

**Key generation and sizes:** all secret material is generated by Python's CSPRNG `secrets`
module — session/bot/API tokens via `secrets.token_urlsafe(32)` = 256 bits of entropy
(`railway/app.py:349`, `railway/db.py:609`, `railway/auth.py:133`). HMAC signing keys are 256-bit
values supplied via environment variables (see Row 48).

**Signing implementation (verbatim, `railway/auth.py:94-111`):**

```python
def _sign(payload: dict) -> str:
    body = _b64e(json.dumps(payload, separators=(",", ":")).encode())
    sig = _b64e(hmac.new(_session_secret(), body.encode(), hashlib.sha256).digest())
    return f"{body}.{sig}"

def _verify(token: str) -> dict | None:
    try:
        body, sig = token.split(".", 1)
        want = _b64e(hmac.new(_session_secret(), body.encode(), hashlib.sha256).digest())
        if not hmac.compare_digest(sig, want):
            return None
        payload = json.loads(_b64d(body))
        if payload.get("exp", 0) < time.time():
            return None
        return payload
    except Exception:  # any malformed token is just invalid
        return None
```

**IV handling:** not applicable — the application performs **no application-layer symmetric
encryption** (no block/stream cipher usage, therefore no IVs or nonces to manage). Confidentiality
in transit is provided by TLS 1.3 at the Cloudflare edge (AEAD suites: AES-256-GCM /
ChaCha20-Poly1305 — see passed rows 4.1.1/4.1.2); confidentiality at rest by the hosting
platform's encrypted volumes (Row 48).

**No deprecated algorithms:** repository-wide case-insensitive search for `md5` and `sha1` across
all Python sources in the deployed service returns **zero matches** (search performed 2026-09-04;
the only hash algorithms present are SHA-256 and HMAC-SHA256, as listed above).

**Key management:** keys are injected at runtime from Railway environment variables (never in
source or VCS), rotation and revocation procedures are documented in `docs/secrets-policy.md`
(provided with Row 48). Per-user session revocation is immediate via the server-side
`session_ver` counter (`bump_session_ver`, verified under passed rows 2.2.1/2.2.2).

## Row 30 — 4.1.4 · Cryptographic modules fail securely / no padding oracle

**Tester asked for:** implementation details showing cryptographic failures return generic,
consistent errors with no information usable for padding-oracle or side-channel attacks.

1. **No padding oracle surface exists.** The application performs no decryption of any kind — no
   CBC mode, no ciphertext parsing, no application-layer encryption at all (see Row 29). Padding
   oracles require a decryption operation whose error behavior distinguishes padding validity;
   there is no such operation in this codebase.
2. **All MAC/token verification is constant-time and collapses every failure mode into one
   result.** `_verify` (verbatim above, `railway/auth.py:100-111`) returns `None` identically for:
   bad signature (checked with `hmac.compare_digest`, line 104), expired token, malformed base64,
   malformed JSON, or any other exception (bare `except` at line 110). The caller cannot
   distinguish *why* a token failed.
3. **Uniform error responses.** Every authentication failure surfaces as the same generic
   HTTP 401 (`{"detail":"unauthorized"}`) or 403; no cryptographic detail, stack trace, or
   distinguishing message is ever returned (default-deny behavior verified live by the assessor
   under passed row 3.1.3).
4. **Constant-time comparison everywhere secrets are compared:** `railway/app.py:101`,
   `railway/auth.py:104`, `railway/auth.py:143`, `railway/auth.py:307`, `railway/billing.py:72`,
   `railway/webhook_dispatcher.py:226`, `railway/app.py:1413`.

## Row 34 — 5.1.4 · Template injection

**Tester asked for:** source/template-configuration evidence that user input cannot reach template
logic.

**The application uses no template engine.** Pages are static HTML files shipped in the repository
and served with literal string replacement of a fixed set of server-controlled placeholder tokens
— never user input. Verbatim serving code (`railway/app.py:2196-2198`, representative of all page
routes at `app.py:2173-2318`):

```python
content = (html.replace("__FAVICON__", _FAVICON_B64)
               .replace("__MEET_PROJECT__", os.environ.get("SONAVE_MEET_PROJECT_NUMBER", ""))
               .replace("__GOOGLE_CID__", os.environ.get("SONAVE_GOOGLE_CLIENT_ID", "")))
```

- Replacement values are exclusively **server environment constants** (favicon bytes, Google
  project number, OAuth client ID). No request parameter, header, or body value is ever
  interpolated into HTML server-side.
- Repository-wide search confirms **zero imports or usage** of Jinja2, Mako, string.Template, or
  any other template engine in application code (`jinja2` appears in the dependency tree only as a
  transitive dependency of the ML stack and is never imported by the service — searched
  2026-09-04).
- Because no template is ever *evaluated*, server-side template injection is structurally
  impossible; there is no expression evaluator for attacker input to reach.

## Row 37 — 5.1.7 · Context-aware output escaping (XSS)

**Tester asked for:** evidence that context-aware output escaping/sanitization is applied to
application outputs, beyond the CSP already verified live.

**Server side:** all API endpoints return `application/json` (FastAPI serialization —
auto-escaped by content type); HTML routes serve static templates only (Row 34), so no
user-controlled data is emitted in HTML by the server.

**Client side:** every dynamic render in the two applications passes untrusted data through a

```javascript
function esc(s){return String(s==null?'':s).replace(/[&<>"']/g,
  c=>({'&':'&amp;','<':'&lt;','>':'&gt;','"':'&quot;',"'":'&#39;'}[c]))}
```

Applied at every sink that renders untrusted data — speaker names (attacker-influenceable via
meeting display names), emails, model IDs, filenames, incident details:

## Row 38 — 5.1.8 · Database injection

**Tester asked for:** evidence of the database access implementation (parameterized queries /
allowlisting).

All database access goes through `railway/db.py` using SQLite **parameterized `?` bindings
exclusively** — user-controlled values are never concatenated into SQL text. The one function that
builds column names dynamically is guarded by a frozen allowlist (verbatim,
`railway/db.py:270-282`):

```python
def mark_bot(bot_id: str, **cols) -> None:
    if not cols:
        return
    # Whitelist allowed column names to prevent SQL injection via f-string (OWASP A03)
    _ALLOWED_BOT_COLS = frozenset({
        "status", "started_ts", "ended_ts", "metered_sec", "meeting_url"
    })
    invalid = set(cols) - _ALLOWED_BOT_COLS
    if invalid:
        raise ValueError(f"mark_bot: disallowed column(s): {invalid}")
    sets = ", ".join(f"{k}=?" for k in cols)   # column names from the whitelist; values bound via ?
```

Note the values themselves are still bound via `?` placeholders — only whitelist-validated column
*names* enter the SQL string. Additionally, all request bodies are parsed through strict Pydantic
models before any value reaches the data layer (verified under passed row 5.1.1), and the SQLite
database is a private file on the application volume — reachable only through this code path, with
no separate network-exposed database service.

## Row 41 — 5.2.1 · Malicious file uploads

**Tester asked for:** evidence of enforced file-type validation and non-executable storage.

**The application exposes no file-upload endpoint at all.** Repository search (2026-09-04) for
`UploadFile`, `File(`, or multipart request *parsing* returns zero upload handlers (the only
`multipart` references are in an outbound HTTP client that *sends* data to a third-party API,
`railway/app.py:879, 931`).

Audio enters the system exclusively as **base64-encoded raw PCM16 frames over the authenticated
WebSocket** (`/api/ws/audio` — token-authenticated and origin-checked, `railway/app.py:537-564`):
fixed sample format (16 kHz mono s16le), decoded with `base64.b64decode` and processed as raw
bytes (`app.py:634`). There is no filename, no MIME type, and no container format for an attacker
to smuggle content through — a "file type" other than raw PCM cannot be expressed on this
interface.

Server-side persistence: capture files are written **by the server** with server-generated names
(sanitized speaker slug + counter — Row 40) as `.wav` under the private `/data` volume. That
directory is **not a static docroot**: nothing in it is ever executed or served as code; audio is
only streamed back through authenticated, user-scoped API routes with audio content types. The
Python process never executes content from the data volume.

## Row 44 — 6.3.1 · Origin header not used for authentication/access control

**Tester asked for:** direct evidence that authn/z decisions rely on session/bearer tokens and
server-side checks rather than the Origin header.

**Authentication inputs are exactly three, none of them Origin** (`auth.get_principal`,
`railway/auth.py` — token sources are the `Authorization: Bearer` header, the `X-Sonave-Token`
header, and HttpOnly session cookies; the query-string source was deliberately removed, per passed
row 2.1.1). Authorization is then decided server-side from the verified session (role/workspace
decoded from the HMAC-signed token + DB `session_ver` check — passed rows 3.1.1/3.1.2).

**The Origin header appears exactly once in the entire service**, and it is a *deny-only*
cross-site-WebSocket-hijacking filter applied **after** token authentication has already succeeded
— it can only reject, never grant (`railway/app.py:551-563`):

```python
# Validate WebSocket Origin to prevent cross-site WebSocket hijacking (CASA AL1 / ASVS V13.5)
_origin = ws.headers.get("origin", "")
_allowed_origins = ("https://usesonave.com", "https://meet.google.com",
                    "https://workspace.google.com", "http://localhost", "http://127.0.0.1")
if _origin and not any(_origin.startswith(o) for o in _allowed_origins):
    logger.warning("ws_audio: rejected disallowed origin %s", _origin)
    await ws.close(code=1008)
    return
```

A request with a forged Origin and no valid token is still rejected (token check at
`app.py:537-549` runs first, closing with code 1008); a request with a valid token gains nothing
extra from any Origin value. CORS/`frame-ancestors` are used only for browser-side embedding
policy, not authorization.

## Row 48 — 6.7.1 · Secure storage of access tokens, API keys, server-side secrets

**Tester asked for:** the documented secrets access-control policy, storage evidence, and
logging/monitoring of access.

**Policy document:** `docs/secrets-policy.md` (submitted alongside this pack) — covers inventory,

**Storage & injection:** all secrets (Google OAuth client secret, session HMAC secret,
`SONAVE_API_TOKEN`, Stripe keys, Recall/Modal/HF tokens) exist only as **Railway environment

**Logging & monitoring:** Railway records dashboard/config access and deployment events in the

event is tracked in the audit `events` table and pushed to the operator in real time
